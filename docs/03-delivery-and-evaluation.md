# Deep Research 工作台开发与评测计划

> **目标计划。** 里程碑、`evaluations/`、Compose、MCP Server 目录与 24 题消融是规划，仓库里尚未建立评测集或这些目录，也不应为空目录占位。当前可运行范围与测试以 [README](../README.md) 和 `apps/api/tests` 为准。

实现按完整闭环、资料与扩展、工程可靠性、评测交付的顺序推进。每阶段产生可演示成果，技术加入以具体需求和验证结果为依据。以下为单人开发的参考安排，按里程碑验收，周数不构成交付承诺。

## 里程碑与实现顺序

| 阶段 | 参考时间 | 实现内容 | 通过条件 |
| --- | --- | --- | --- |
| M0 | 第 1 周 | 目录、数据库迁移、模型与工具接口、项目 CRUD、最小前端 | Compose 启动；项目隔离与 Schema 测试通过 |
| M1 | 第 2 周 | 单 Researcher、计划、搜索阅读、证据、引用报告、表格 | 一个真实研究完整跑通；从结论可回到原文 |
| M2 | 第 3 周 | 资料解析、混合检索与重排、Skills、项目 MCP Server | 同一问题结合上传资料；MCP 独立进程可调用 |
| M3 | 第 4 周 | 主控与并行 Researcher、覆盖矩阵、补充研究、上下文压缩 | 可观察并行；预算和轮数有界；局部失败有结果 |
| M4 | 第 5 周 | Outbox、Worker 租约、检查点、事件重放、人工介入、增量研究 | 关闭页面与结束 Worker 后可恢复；新增对象复用证据 |
| M5 | 第 6 周 | 评测集、消融实验、回归 CI、成果导出、演示与文档 | 数据与轨迹可复现；公开案例、结果表与限制说明齐全 |
| M6 | 额外阶段 | 演示稿、代码沙箱、动态网页浏览器 | 数据分析隔离；多个交付物事实一致 |

Tracing 在 M0 接入，并贯穿所有阶段。检查点在 M1 建立，M4 完成崩溃恢复与幂等机制；基础权限和错误处理从第一阶段落实。

## 建议代码组织

```text
research-workbench/
  apps/
    web/                         # Next.js 工作台
    api/app/
      api/                       # 路由、身份、请求校验
      domain/                    # 项目、运行、证据、成果
      agents/
        graphs/                  # 主控图与 Researcher 子图
        nodes/                   # 规划、缺口、综合、校验
        schemas/                 # 状态和结构化结果
      tools/                     # 工具注册、策略、Schema
      retrieval/                 # 解析、分块、召回、重排
      services/                  # 预算、证据、版本、恢复
      infrastructure/            # DB、存储、模型、队列适配
      workers/                   # 执行、派发、恢复
      observability/             # Trace、日志、指标
    mcp-server/                  # 资料库独立 Server
  skills/                        # 研究方法与输出规则
  migrations/
  evaluations/
    datasets/                    # 公开或合成样例及人工标注
    graders/
    experiments/
  tests/
    unit/
    integration/
    recovery/
    e2e/
  infra/                         # Compose 与部署配置
  docs/                          # 架构、ADR、评测与演示
```

先使用模块边界，不为每个模块启动一个服务。单一 run_id 贯穿业务日志、Trace 和事件；子任务附带 task_id 和 attempt。

## 最小纵向切片

第一条切片研究两家产品、三个维度，只使用公开网页：

1. 创建项目并提交任务，返回 run_id。
2. 生成结构化计划，用户接受后执行。
3. 搜索并读取正文，保存来源和原文摘录。
4. 生成结论，检查引用 ID 与摘录。
5. 渲染报告与对比表，点击结论显示证据。
6. 导出 Markdown 与 CSV，打开历史研究仍可查看。

这条切片完成后再扩展 RAG、多 Agent 与恢复，不先开发大量缺少后端支撑的页面。

## 评测集构建

初始 24 道题，覆盖 8 道竞品、6 道行业、4 道上传资料结合、3 道增量研究、3 道冲突与缺失信息。另建工程故障测试，避免把故障测试混入业务质量平均分。

18 道作为开发集，6 道保留为最终测试集。样本量只适合项目级比较，不宣称广泛统计结论；报告展示每题结果和重复运行波动。持续补充失败样例，但冻结最终测试集。

每题记录：question、scope、source_snapshot_ids、required_dimensions、reference_facts、supported_claim_evidence_pairs、known_conflicts、missing_fields、expected_output_schema。参考答案来自可核查原始资料，保留标注日期和版本。

引用评测至少制作 100 组 Claim 与 Evidence 人工标注对，区分 fully_supported、partially_supported、contradicted、unrelated。开发者和一位可邀请的独立复核者对部分样本复核；无人复核时如实记录单人标注限制。

来源访问和搜索索引可能变化，因此分为固定快照离线评测与实时联网评测。离线模式用于稳定回归；实时模式用于观察真实搜索表现，记录日期、错误与实际来源。

## 指标定义

| 指标 | 定义 | 评分方式 |
| --- | --- | --- |
| 维度覆盖率 | 有实质回答的必需维度数 / 必需维度总数 | 人工标注为主，模型辅助 |
| 引用支持率 | 被对应原文充分支持的已引用事实结论数 / 已检查引用事实结论数 | 固定样本人工标注，语义评审经校准 |
| 引用完整率 | 带有效证据的可核查事实结论数 / 全部可核查事实结论数 | 引用解析与人工抽样 |
| 关键事实准确率 | 正确的参考事实数 / 已核对的参考事实数 | 与原始来源及口径比较 |
| 缺失标注准确性 | 正确标注未确认的必需字段，以及错误断言数量 | 与缺失样例比较 |
| 检索 Recall@k | Top k 中命中的相关证据数 / 标注相关证据数 | 固定来源语料 |
| 冲突识别 | 正确识别冲突数、误报数及漏报数 | 人工冲突集合 |
| 恢复成功率 | 成功恢复并满足幂等约束的故障测试数 / 故障测试数 | 自动故障注入 |
| 增量复用 | 新 run 复用有效证据的数量与占比 | DB 与调用轨迹 |
| 延迟 | 计划时间、研究时间、总时间的 p50 与 p95 | 同一运行配置 |
| 成本 | 每题模型与工具调用费用，含未知费用标记 | Usage ledger 与供应商对账 |

“未找到信息”不计为实质回答，但可以计入缺失标注指标。引用 ID 存在不能等同于语义支持正确。可访问 URL 也不能等同于引用内容成立。

自动评测先检查 Schema、引用存在性、摘录定位、对象和维度数量，再用模型评审语义支持和覆盖。模型评分需与人工标注校准，不能作为唯一真实性判断。Langfuse 存实验结果与轨迹，项目代码实现具体评分器。

## 对照与消融实验

| 实验 | 配置 | 要回答的问题 |
| --- | --- | --- |
| A | 单次模型回答加一次搜索，无自主补充 | 最简单基线能达到什么效果 |
| B | 单 Researcher，允许搜索阅读循环 | 自主循环是否提高覆盖与引用质量 |
| C | 多 Researcher，其余配置与预算尽量一致 | 并行是否降低延迟，是否增加重复与费用 |
| D | 上传资料场景，向量检索与混合检索重排对比 | 检索改进能否找到更准确的原文 |
| E | 有无缺口检查与引用校验 | 检查节点是否改善质量，代价是什么 |
| F | 增量追加与全部重跑对比 | 复用能否节约调用，同时保持事实正确 |

主要比较固定模型、相同数据和明确预算；多 Agent 与单 Agent 分别报告相同总预算及相同完成目标两种设置。先在开发集定位问题，再在保留集复核；关键配置至少重复 3 次，报告分布和失败，不只选最好一次。

MCP 验证协议接入和权限一致性，不以“使用 MCP 后准确率提高”为目标。Skills 比较适用任务的结构完整性与上下文开销。模型路由、压缩、沙箱等扩展各自需要单独实验。

## 必需工程测试

| 测试 | 故障或动作 | 预期结果 |
| --- | --- | --- |
| 派发一致性 | 数据库提交后、队列发送前停止派发器 | 重启后发送未完成 Outbox |
| 重复派发 | 同一 run 消息发送两次 | 只有有效租约 Worker 发布成果 |
| 检查点窗口 | 工具完成后、图检查点提交前结束 Worker | 复用已记录结果，最终证据与成果不重复 |
| 租约过期 | 旧 Worker 停顿，新 Worker 接管后旧 Worker 恢复 | 旧 epoch 无法提交业务结果 |
| 外部超时 | 模型或搜索超时与限流 | 有限重试、预算记账、可解释失败 |
| 预算并发 | 多个 Researcher 同时申请调用 | 原子预留阻止无约束超支 |
| 暂停与取消 | 在工具运行中提交命令 | 停止新增调用，在边界落实终态 |
| 计划修改 | 暂停后改计划，旧子任务晚到 | 旧版本不污染新汇总 |
| 事件重连 | SSE 断开后带 Last-Event-ID 连接 | 有序重放，前端去重 |
| 访问隔离 | 用户 B 访问用户 A 的 run、证据、下载或 MCP 资源 | 拒绝访问且无数据泄漏 |
| URL 防护 | URL 重定向到本机或内网 | 阻止读取 |
| 提示注入 | 网页含要求泄露密钥或调用越权工具的文字 | 内容不能扩大权限；记录异常 |
| 增量版本 | 停用来源或编辑事实 | 受影响结论待检查，历史版本可查看 |

CI 运行不联网单元与集成测试；固定快照回归通过手动或定时触发。实时联网评测单独执行，避免外部服务波动阻塞每次提交。P2 沙箱需要新增资源限制与网络隔离测试。

## 秋招演示脚本

建议准备 5–8 分钟完整演示：

1. 输入研究目标并上传一份背景资料。
2. 修改研究计划的一个维度，启动研究。
3. 展示 Researcher 并行、证据增长与 Trace。
4. 结束 Worker 再重启，展示恢复与已有结果复用。
5. 查看报告，点击一个结论定位原文，并检查一个冲突或未确认项。
6. 新增一个竞品，展示增量研究和版本差异。
7. 展示评测结果及质量、时间、成本的取舍。

提前保留可回放的固定快照案例，同时如实区分实时演示与回放，避免网络失败导致作品无法展示。

## 最终交付

- 可本地一键运行的工作台，以及可选在线 Demo。
- README，包括启动、环境配置、样例任务与已知限制。
- 架构图、核心数据关系与 4–6 篇设计决策记录。
- 公开评测样例、评分脚本、逐题结果和对照实验。
- 研究案例：任务、计划、证据、报告、表格与调用轨迹。
- 故障恢复与增量研究的演示视频。

建议记录的设计决策包括：选择 LangGraph、使用 pgvector、证据与结论分离、队列与检查点分工、MCP 边界、多 Agent 与预算策略。

简历描述最终围绕可验证事实填写：实现了哪些能力，在多少道题上与什么基线相比得到什么结果，在何种条件下完成故障恢复。未测得的提升、未完成的功能和未验证的生产规模不能写成成果。
